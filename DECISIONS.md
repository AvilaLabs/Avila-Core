# Decision index

This file records accepted strategic decisions and links to architectural
decision records (ADRs). “Proposed” items are intentionally reversible.

| ID | Status | Decision |
| --- | --- | --- |
| S-001 | Accepted | Product and repository identity are **Avila Core**. |
| S-002 | Accepted | Core begins with a technical question and evidence contract, not a solver catalog or blank workflow canvas. |
| S-003 | Accepted | Core is infrastructure for people and software agents; it does not present Avila Labs as the domain authority for every supported method or require a professional reviewer for ordinary technical verdicts. |
| S-004 | Accepted | Public positioning centers on rigorous computational evidence, not implementation trends. |
| S-005 | Accepted | `PASS`, `FAIL`, `INCONCLUSIVE`, and `NOT_EVALUATED` are distinct first-class states. |
| S-006 | Accepted | Avila should be paid for admissibly resolving a contract, not for returning `PASS`. |
| S-007 | Accepted | Customer evidence must be portable and independently inspectable. |
| S-008 | Accepted | Scientific adapters may wrap existing tools in any suitable language; Rust is the authority and orchestration boundary, not a mandate to rewrite solvers. |
| S-009 | Accepted | The initial application is local-first and compatible with private or air-gapped deployment. |
| S-010 | Accepted | Specimen and unavailable capabilities must fail closed and never create cosmetic success states. |
| S-011 | Accepted | The repository is `AGPL-3.0-only` except for separately reserved branding assets. The local runtime and verifier remain open adoption surfaces, and a modified network-interactive Core must offer its corresponding source to its users. See [ADR-0012](docs/adr/0012-agpl-license-and-work-product-boundary.md). |
| S-012 | Proposed | The first vertical proof composes transport, activation, shutdown dose, uncertainty treatment, and requirement evaluation. The choice must be justified by representative problem evidence before it becomes a supported product claim. |
| S-013 | Accepted | Publish Core's semantic profiles, conformance vectors, package format, and verifier interface under the repository license so the judgment layer is independently auditable. Core mechanisms are not withheld for patent protection; additional permissive interoperability terms remain an explicit future decision. See [ADR-0012](docs/adr/0012-agpl-license-and-work-product-boundary.md). |
| S-014 | Proposed | JSON remains the canonical interchange. A textual `.acore` front end is built only after semantic fixtures stabilize and measured authoring evidence justifies it. |
| S-015 | Accepted | A Core verdict is a conditional derivation from admitted records under named rules and authorities. It is not, by itself, scientific truth, certification, or regulatory approval. |
| S-016 | Accepted | The `v0.1` contract model, capability manifests, and planner are retired. The `v0.2-draft` contract, which carries its bounded question, and the registry snapshot compiled by `avila-core-compiler` are the only authoritative document forms; package selection returns as an SC-5 and SC-8 binding pass over compiled snapshots. |
| S-017 | Accepted | `CASE-000` is the first composed internal integration specimen: the frozen ACTINV 1.0.1 inventory feeds Aftermatter R0, Core admits the recorded claims, and both bounded requirements produce technical `PASS`. No review is required for those verdicts. The case does not select the first external vertical, qualify either tool, or count as pilot evidence. |
| S-018 | Accepted | The first runnable case workflow separates raw-byte integrity, identity binding, semantic compilation, campaign evaluation, and deterministic replay. Omitted artifact roots are `not_checked`; supplied roots with missing or different bytes fail closed. A matching digest proves identity only and does not alter qualification or review state. |
| S-019 | Accepted | `CASE-000E`: Core executes Aftermatter through a named case-specific adapter over verified bytes and an exact executable, writes and verifies an execution receipt, and generates the output claims from the fresh bytes. An omitted executable leaves a step `not_run` with its committed claims as recorded attestations; a supplied executable must match its bound identity, complete, and reproduce claims that bind, or the run is rejected. No horizontal runner or adapter protocol is built. |
| S-020 | Accepted | CASE-000 revision 2 executes ACTINV 1.0.1 as well, through Aftermatter's frozen R0 builder under a digest-pinned Python interpreter, with the builder script and the ACTINV executables as hash-bound inputs of the step. The activation step's problem, inventory, and decay metadata become executed outputs, so no output claim in the case is authored. The Aftermatter repository is not modified for this; a tool that must change to be executed is a finding, not a patch. |
| S-021 | Accepted | The case runner performs SC-12 execution memoization: a step whose planned invocation identity (capability digest, parameters, staged input identities, arguments, environment, timeout) equals a committed completed receipt's, and whose recorded outputs all verify at bound artifact identities, is reused without running and without needing the executable. Any difference is reported by typed change class (input bytes, input binding, parameters, capability, invocation, no or incomplete receipt, outputs unavailable) and reruns exactly that step; dependency follows content, so a rerun whose outputs are byte-identical leaves its consumers reused. `--plan` reports the analysis without running; `--no-reuse` forces fresh execution. |
| S-026 | Superseded by S-027 | The first staged-review model separated agents from people but incorrectly retained mandatory accountable review as a technical `PASS` gate. See the historical [ADR-0009](docs/adr/0009-staged-agent-review.md). |
| S-025 | Accepted | A qualification record is a method owner's document binding one adapter and one exact executable to a kernel applicability predicate over facts the adapter extracts from verified inputs. The runner evaluates the envelope before a step runs or is reused and attaches the result to the step and its claims; the campaign leaves a bounded or enclosure requirement `NOT_EVALUATED` when its evidence lies outside the envelope or its position is unknown, with the failed terms named. A claim without any envelope is still evaluated; enforcing qualification for every bounded verdict is deferred to the semantic profile. See [ADR-0008](docs/adr/0008-qualification-envelopes.md). |
| S-024 | Accepted | A library requirement set states what any contract in its domain must address. A case package may bind one as a `requirement_set` document and must then declare which contract requirements cover each entry and, for the rest, a reason and an accepting owner. `run` assesses coverage after compiling and before executing: an unstated omission the set requires to be stated, or coverage only on a weaker basis than the set's minimum, is incomplete and stops the run. Coverage is a report about the contract, not a verdict about a design. The first set is the shielding library's, written by the case author for a research specimen. |
| S-023 | Accepted, refined by S-032 | `CASE-001` is the first generative-loop case: a shielding configuration search with a free candidate input, an unqualified screen that can satisfy only a nominal-basis requirement, OpenMC transport that satisfies the bounded one, margins on every verdict, and a campaign log. A supplied free input invalidates every step it reaches: committed claims are withheld, fresh outputs bind by receipt, replay is not applicable. Required environment keys are invocation identity by name. Byte stability of a seeded stochastic step is the capability's obligation. |
| S-022 | Accepted | Core's intended primary use is the generative loop: an agent proposes candidates, Core says exactly what fails and why, and every run grows an engineering constellation. Requirements remain fixed by the requester while the agent searches. A configured connected-agent practicality gate may return a finalist or present it to the user, but neither a human nor a professional review is required for Core's technical verdict. Verification of existing work is a use, not the goal. See [The generative loop](docs/strategy/GENERATIVE_LOOP.md). The first domain is shielding configuration search. |
| S-027 | Accepted | Technical verdicts and presentation routing are separate. Claims and campaign evaluation contain no review decisions; review absence never suppresses `PASS`. Core works without an AI integration. If configured, an instructed connected-agent presentation gate receives the exact post-campaign dossier and may `present_to_user`, `request_changes`, or `abstain`; it never changes the verdict or claims professional authority. User acknowledgement is a separate product-policy event. See [ADR-0010](docs/adr/0010-technical-verdicts-and-optional-presentation-gates.md). |
| S-028 | Accepted | `CASE-002` composes CASE-001's search with coupled neutron-photon transport and ACTINV activation on each layer's tallied spectrum, evaluates six requirements with a 7/3 uSv/h allocation of the design point, and is the first pre-registered experiment: `PROTOCOL.md` fixes the arms, measurements, and outcomes before any campaign. Activation is a nominal search guide and a stated coverage omission at the library's required bounded basis, with the missing capability named, because Core refused the contract that mapped it as coverage. The runner's rule that a package binds exactly the output slots an adapter lists stands; an output no bound data can produce is not a slot. Cases are blessed with `examples/cases/tools/bless.py` and re-hashed with `rehash.py`. |
| S-029 | Accepted | `CASE-003` is the second domain: a strip-heated layered heat spreader, screened by a one-dimensional resistance estimate and decided by two-dimensional finite-element conduction whose hotspot is an `interval` claim under the `enclosure` basis, the home for deterministic discretisation brackets. Its finite-element qualification record is the first to bind validation evidence, a NAFEMS T4 reproduction within 0.005 percent. The case runner resolves a capability's path before launching it, so an interpreter must be a real file inside its environment; the runner is not changed for this. |
| S-030 | Accepted | Package self-consistency is not integrity. An adversarial designer with write access obtained undeserved verdicts by rewriting limits, scripts, receipts, and manifests together, while every refusal that did not require rewriting the package held. Every campaign log line therefore carries the identities it was evaluated under (manifest, compiled snapshot, every document's digest, reused receipts), and `run --expect-manifest` refuses, before anything is compiled, a package whose manifest digest differs from the requester's pin; the search tools pin the package when an arm is initialised. The pin is the requester's external anchor until receipts and manifests are signed, which remains open. |
| S-031 | Accepted | The speed tier's first attempt is on record: a verified one-dimensional multigroup S_N solver with an adjoint, a VITAMIN-J-175 library built from OpenMC, and CADIS weight windows. Against 28 logged Monte Carlo designs the solver is within the interval 15 times and biased low for lead, concrete, and water; without synthetic acceleration it takes seconds to a minute per candidate and its adjoint costs more than the Monte Carlo run, so the windows lost to the existing analytic ones. The result is recorded as a negative and the solver is bound to no case until diffusion synthetic acceleration makes it cheap. |
| S-032 | Accepted | Operator-supplied environment values are runtime-only. Receipts bind required key names and the content identities those keys locate, but never serialize operator values; this avoids leaking host paths, credentials, tokens, or license-server details without weakening invocation identity. See [ADR-0013](docs/adr/0013-runtime-environment-confidentiality.md). |
| S-033 | Accepted | The speed tier's second attempt is recorded as a negative and discarded. A Newton-GMRES acceleration of the slab S_N thermal iteration (branch `coupled/slab-sn-dsa`, commit `bd0a03e`, never merged) passed its own unit tests, but on the real VITAMIN-J-175 library and an 85 cm three-layer candidate it ran no faster than the unaccelerated solver (57 s against 51 s forward), its adjoint did not finish in fifteen minutes, and it reported a neutron dose rate about twice the unaccelerated value (84.3 against 43.2 uSv/h). A screen that changes the answer is not a screen. The S_N solver stays bound to no case; a future acceleration attempt starts from S-031's verified solver with an agreement test against it as its first gate. The multigroup library remains generated, not committed. |
| S-034 | Accepted | An external architecture and execution proposal dated 4 September 2026 and pinned to `3be5902` is kept as reference architecture, not as the work order ([proposal](docs/roadmap/proposals/2026-09-04-architecture-and-execution-roadmap.md), [review](docs/roadmap/reviews/2026-09-04-architecture-proposal-review.md)). Each of its repository observations was checked against the source and measured: every one is literally true and none is a dominant cost at today's campaign scale. Work proceeds in the order of measured uncertainty: the Core-feedback ablation (EXP-002) with the shortcut-refusal criterion folded in; then the cheap, precedented integrity fixes (strict qualification, candidate validation at the boundary, process-group timeout, locked single-write log append, an opt-in verified-hash cache, extraction of rendering and logging from the case runner); then signed receipts and manifests and an independent verifier. The proposal's session, store, obligation-graph and scheduler milestones are considered only after the scored EXP-002 result and a release-build baseline show a campaign that needs them. |
| S-035 | Accepted | Closes the ADR-0008 clause 5 deferral in mechanism: a contract's `execution_policy.require_qualification` makes a bounded or enclosure requirement `NOT_EVALUATED` (CORE-A4402) when its admitted evidence carries no qualification assessment at all; left at its default, the same evidence is still evaluated but the verdict carries an informational CORE-A4403 reason, so a profile that permits unqualified evidence never does so silently. Nominal-basis requirements are exempt either way; categorical requirements have no basis and stay governed by CORE-A4401 alone. CASE-000's two bounded `PASS` verdicts now carry CORE-A4403. CASE-001, CASE-002 and CASE-003 do not yet set the flag: their screen-step geometry claims (mass, thickness, areal mass) carry no qualification record, so enforcing it today would turn those bounded requirements `NOT_EVALUATED`; the next step is an honest, limited qualification record for that arithmetic, then the flag. |
| S-036 | Accepted | A registry role may declare `input_schema`, an embedded JSON Schema in the compiler's supported subset (type, properties, required, additionalProperties, items, enum, const, oneOf, the canonical-decimal pattern, description; no `$ref`), for the documents that fill it as a free input. A schema outside that subset is refused at registry compile time (CORE-R3501). The runner validates every supplied free input against its role's schema before anything is staged or executed, with the same shape validator the compiler uses; a violation refuses the run under CORE-X1301 with one finding per JSON Pointer. CASE-001 and CASE-002 declare `avila.shielding/candidate/v1`, CASE-003 declares `avila.thermal/candidate/v1`, all re-blessed with unchanged verdicts. Material vocabulary stays the capability's job, not the schema's. |
| S-037 | Accepted | A step timeout kills the child's whole process group, not only the runner's direct child, so an adapter that shells out to a solver cannot leave it running after Core reports the timeout; the timed-out receipt's limitations say so. The run-attempt log append is one write under an exclusive advisory lock held across the pre-append lineage revalidation, so two local writers racing to append the same attempt id cannot both be admitted or tear each other's line. Both guarantees are single-host and process-local: no signature, no cross-host coordination, and no defence against a writer that bypasses the lock. See ADR-0007 and ADR-0014. |
| S-038 | Accepted | `avila-core run --hash-cache PATH` adds an opt-in, off-by-default cache of verified digests for large operator-supplied artifacts resolved under a `--source-root`, keyed by canonical absolute path, size, modification time, and device and inode where the platform exposes them. A hit is reported as the distinct `verified_cached` integrity state, never plain `verified`, and is still compared against the manifest's bound identity exactly as an uncached digest would be, so a stale or malicious entry still fails closed. Package documents and any artifact inside the case directory are never eligible. The cache trusts that operator-owned artifact roots keep a file's size and modification time whenever its bytes are unchanged; it is not a defence against a designer with write access to those roots, and the requester's manifest pin (S-030) is unaffected. |
| S-039 | Accepted | A qualification record may name `covered_output_slots`, the output slots of its bound capability it covers; omitted, it covers every output the capability produces, unchanged from before. The runner attaches the evaluated envelope only to a claim on a covered slot, so a step that produces both a qualified geometry claim and an unqualified estimate from the same execution carries the assessment on the first and none on the second; an uncovered claim can still satisfy only a nominal-basis requirement. CASE-001, CASE-002 and CASE-003 each bind a qualification record for their screen capability scoped to its mass or areal-mass and thickness slots, stating the arithmetic identity over the bound materials table as its basis, binding no validation evidence and saying so, with an envelope no wider than the case's search box. `execution_policy.require_qualification` is now `true` in all three contracts; every verdict's status, rule and value is unchanged and CORE-A4403 no longer appears in their committed reports. Closes the S-035 deferral for these cases. See [ADR-0008](docs/adr/0008-qualification-envelopes.md). |
| S-040 | Accepted | Manifests and execution receipts can be signed (ADR-0015). A requester key signs a case package's manifest: the digest of the manifest with the signature document's own entry removed, canonicalised, so signing before and verifying after binding that entry compute the identical digest. A runner key signs each execution receipt and each campaign log line (the canonical line with the `signature` member removed, then re-serialised with it appended). `run --trust-root FILE` refuses a package before compilation unless its manifest signature verifies against a listed requester key, and reuses a committed receipt under SC-12 only when its signature verifies against a listed runner key; without a trust root every signature is reported `unsigned`, `not_checked` or `invalid`, never `verified`. `execution_policy.require_signatures` refuses an unsigned package, reuse or execution outright, mirroring `require_qualification`; none of the three loop cases sets it yet. Writing the adversarial tests surfaced and closed an unrelated SC-12 gap: a committed receipt's `case_id` was not part of reuse comparison, so a byte-identical receipt copied from another package would have been reused; `ChangeClass::DifferentCase` now refuses it, signed or not. CASE-001, CASE-002 and CASE-003 are signed with one public example keypair committed under `examples/keys/` and stated to prove nothing. `ed25519-dalek` is the workspace's first cryptographic dependency. |
| S-041 | Accepted | `verifier/avila_core_verify.py` is a standard-library-only Python verifier that imports no Core crate. It re-derives canonicalisation, unit scaling and the four-state verdict calculus from the semantic-core vectors and the ADRs, never from Rust source, then re-hashes package identity, recomputes every execution receipt's invocation identity and output bindings, binds claims to receipts and artifacts, re-derives every numeric and categorical verdict and exact margin against the committed campaign report, and verifies ADR-0014 lineage logs. It agrees with every canonical, unit-scaling and verdict-calculus vector, 12 of 15 campaign fixtures (three named as needing a compiled dataflow graph or registry role table outside its profile), all 15 committed receipts and both lineage logs, and runs with zero mismatches on CASE-000, 001, 002, 003, 008 and 009 with whichever artifact roots exist; five mutation classes are each named. Not yet checked, by name: qualification envelopes, coverage, presentation gates, `campaign_sha256`, and ADR-0015 signatures. |
| S-042 | Accepted, refined by S-046 | The independent verifier checks ADR-0015 signatures with a from-scratch Ed25519 implementation (RFC 8032, standard library only) proven against the RFC's own test vectors and every committed signature document, given a trust root; without one it reports `not_checked`, never `verified`. Its qualification-envelope check is structural (term text, state self-consistency, `covered_output_slots`), because Core does not persist the applicability facts an adapter extracted, only the record's authored predicate and the resulting state; re-deriving an envelope boolean from outside therefore remains impossible until the runner records those facts, which is now a named gap. Mutations of a signature byte, a key id, a re-blessed manifest's stale signature, and an envelope term are each detected. |
| S-043 | Accepted | `execution_policy.require_signatures` is now set on CASE-001, CASE-002 and CASE-003: each was re-signed and re-blessed with every verdict unchanged, and `run` without `--trust-root` refuses under CORE-X1005 before anything is compiled. The CASE-002 campaign adversarial checker verifies a log row's own ADR-0015 signature before believing any of its fields: `adversarial_check.py --trust-root FILE` recomputes each row's canonical digest and checks the detached Ed25519 signature against the listed runner key, so a row edited after Core wrote it, however slightly, classifies `refused` rather than passing as `honest`; unsigned or unchecked rows classify exactly as before. The workbench exposes the same options — `avila-core-app --trust-root FILE --runner-key FILE`, with Trust root and Runner key fields in case setup. |
| S-044 | Proposed | External-checker claims may be declared `optional` (ADR-0016): a pointer that resolves to no value leaves the claim absent instead of failing extraction, and the absent slot names are recorded; a present-but-malformed value still fails. The claim-coverage check compares against required slots only. Independently, the SC-12 reuse comparison now includes the adapter descriptor's byte digest, so an extraction-map or claim-mapping edit that leaves the argument vector untouched invalidates a committed receipt instead of reusing it. See [ADR-0016](docs/adr/0016-optional-external-checker-claims.md). |
| S-045 | Accepted | Package-declared checkers extract numeric uncertainty directly (ADR-0017): `interval` claims select explicit lower/upper quantities with an optional nominal, and `unquantified` numeric claims select a nominal estimate, both under the existing authoritative-number boundary. Bounds remain provider assertions; no midpoint, error allowance, or qualification is created by extraction. `optional` stays an exact/categorical axis only — interval and numeric-unquantified claims are always required by the descriptor. Merging this with ADR-0016 surfaced that both sides had added the adapter-descriptor digest to SC-12 reuse comparison; the comparison is kept once with the more precise change detail. See [ADR-0017](docs/adr/0017-external-checker-numeric-uncertainty.md). |
| S-046 | Accepted | Every qualification envelope assessment now persists the applicability context it was evaluated over (ADR-0018): `EnvelopeAssessment` and each claim's `qualification` carry the exact kernel applicability context — the adapter-reported facts with their declared sources and each staged input's media type and identity — so an envelope verdict is re-derivable from committed documents alone. The evidence-claims schema refines in place to require it. The independent verifier re-evaluates each scope term over the persisted context, compares per-term results and aggregate state against the recorded ones, and binds each context input's identity and every fact's `plan:<invocation>` receipt reference to the step's committed receipt; a qualified claim with no context is a mismatch. CASE-001 and CASE-003 were re-blessed and re-signed with every verdict unchanged; CASE-002's claims await a deliberate actinv re-pin and are named as mismatches meanwhile. What remains unproved, by name: whether the adapter's extraction from the staged bytes is correct — the facts stay producer assertions with provenance. See [ADR-0018](docs/adr/0018-persisted-applicability-contexts.md). |
| S-047 | Accepted | The independent verifier re-derives requirement-set coverage (S-024): for a case whose manifest binds a `requirement_set` document it re-assesses the declaration — mapping keys against the set, each mapped contract requirement's kind/comparison/basis against the entry's, omission reasons and accepting owners, the `must_state`/`may_omit` policies — and reports a derived `incomplete` as a mismatch, since a conforming `run` refuses before evaluation and could not have produced the committed claims. The per-entry report is never committed, so the derived status is the only committed observable; CASE-001, 002, 003 re-derive complete and the unbound cases get no check. The verifier also recomputes the committed report's `campaign_sha256` over its semantic body (the identity body always carries `findings`; the report omits it when empty), binding findings and admissions fields the verifier does not individually re-derive. Mutations named: a dropped bounded cover, a deleted stated omission, a mapping to a requirement that does not exist, a raised `minimum_basis` in the bound set, and an edited `findings` entry. The remaining named-outs are presentation-gate realisation and recompiling the compiled snapshot. |
| S-048 | Accepted | The case runner's engine core is split out of `case_run.rs` into named submodules under the same golden CLI-output diff that proved the earlier extractions: `runner.rs` carries `Runner` — input staging, invocation planning, SC-12 reuse, receipt verification and output promotion (the step-execution core); `replay.rs` carries SC-12 change-class computation, claims-to-package binding checks and expected-report replay; `gates.rs` carries presentation-gate materialization and request identity; `stderr.rs` carries bounded, redacted diagnostic capture; `tests.rs` carries the workflow's test module. `case_run.rs` keeps the public report types, option parsing and `execute_case` orchestration. All 16 golden cases diff byte-identical and the suite is unchanged at 120 runner tests; this is code motion only — receipt identity, reuse classes and verdict behaviour are untouched. `run_step` itself remains a long function inside `runner.rs`; further intra-function decomposition is not queued. |
| S-049 | Accepted | `core_constellation` projects one explicitly selected campaign log in record order — every line with its raw digest, case id, status, supplied inputs, verdict margins and requirement statuses, plus lineage fields (attempt id, generation, candidate state and its digest, recorded changes, parent attempt/line/digest) where the line carries an ADR-0014 record — and a derived summary (roots, leaves, max generation, distinct candidate states, requirement-status counts). It reuses `parse_attempts`/`validate_history`, so every line validates before any filter runs: a tampered or incomplete tail is an error even when the selection sits earlier, and a missing file is an error, never an empty constellation. Optional `id`, `case_id`, `offset`, `limit`; absence reports `no_match_in_record`. The view is recorded-only — it names `lineage_validation: consistent` while signatures stay `not_checked`, it follows no referenced artifacts, and the derived summary is a projection, not evidence admission. Pre-`schema_version` logs stay out of profile rather than being silently widened. Wired through the shared catalog so CLI (`avila-core constellation`), `tools call`, MCP, and the workbench's Attempt constellation entry share one implementation; the catalog↔workbench sync test now covers eleven tools. |
