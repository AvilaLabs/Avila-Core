## Runner-chain check (receipt byte identity vs semantics)

The `receipt` premises in `context.bind` carry state `checked` — they name
which receipt *document bytes* were re-hashed into the bound context. Nothing
in the record, the report text, or the verifier claims receipt semantics,
successful execution, signature verification, or a discharged runtime goal:
the `checked`/`verified` vocabulary distinction is preserved (receipts can
only ever be `checked`; `verified` is reserved for digests matched against
an attestation). ADR-0026 §Limitations states the same boundary.

## Remaining limits (honest, not bypasses)

- The observed chain is persisted only when a workspace exists; a run that
  executes nothing binds receipts/artifacts in the in-memory observed
  evaluation but writes no `derivation.json`. The `run` CLI has no
  `--derivation` output flag.
- `receipt` premises are byte identity: the bytes supplied hashed to that
  document identity. They do not verify the receipt's signature or content.
- The verifier replays the rules this profile uses; unsupported rules or
  unavailable bound material report `not_checked`, never `verified`.
- The end-to-end workspace persistence path is covered by the env-gated
  full-execution test; no pinned executable (`python3`, `aftermatter-cli`)
  is available in this environment, so live `derivation.json` output was
  verified by construction and unit test rather than by a real run here.
- Digest-only `campaign-report.json` remains the committed replay
  comparison; promoting the observed report is a separate versioned
  decision (ADR-0026 §4).
